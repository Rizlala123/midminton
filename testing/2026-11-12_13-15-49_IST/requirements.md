# Target-PC prerequisites, setup and models

Date: 12 November 2026. Execute these steps **only on the testing PC**. No setup or testing was performed on the authoring PC. Paths below are examples; open PowerShell in your copied project's root, including when its path contains spaces.

## Required software and hardware

- Windows 10/11 x64, current stable Rust MSVC toolchain, Microsoft C++ Build Tools with Desktop development with C++, and WebView2. Follow [Tauri Windows prerequisites](https://v2.tauri.app/start/prerequisites/#windows). C++ tools are build prerequisites, not inference libraries.
- Node.js >=22.12 (an actively supported Node LTS meeting this minimum is preferred), npm, Git and Python **3.11 or 3.12 x64**. The code declares >=3.11; future Python versions need wheel-compatibility validation.
- FFmpeg and ffprobe on PATH, built with libx264; HDR also requires zscale/tonemap support. Use [official FFmpeg download links](https://ffmpeg.org/download.html); review redistribution terms before bundling.
- Import requires video-stream duration metadata (or a Matroska DURATION tag). If neither is present, remux to MP4 first; container duration alone can include an unrelated audio tail and is not accepted as video length.
- Target: RTX 3050 4 GB VRAM, 16 GB RAM, enough free disk for toolchains, environments, models, proxy and export. Start with at least 15 GB free for setup and trial recordings, then measure actual use. No guaranteed throughput is claimed.
- First-time internet for dependencies/weights; no API account/key or paid service is required. GPU is optional; manual scoring/export do not need a model.

```powershell
py -3.11 -m venv .venv

```

If Python 3.12 is selected, use `py -3.12` consistently instead. `MIDMINTON_PYTHON` lasts for this terminal and apps launched from it. For an installed app, set the variable for your user or launch the installed executable from a terminal that sets it. Set it to the executable path only, without extra arguments or literal quote characters.

Optional GPU alternative: in a **separate clean environment**, install `python[gpu,export,test]` instead of `python[vision,export,test]`. Do not install `onnxruntime` and `onnxruntime-gpu` together: both expose the same module. Follow the current [ONNX Runtime CUDA/cuDNN compatibility matrix](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html#requirements). Confirm the CUDA provider actually loads on this laptop. Merely seeing an NVIDIA GPU or installing Ollama is insufficient.

```powershell
# GPU alternative, only in its own clean virtualenv:
.\.venv\Scripts\python.exe -m pip install -e ".\python[gpu,export,test]"
.\.venv\Scripts\python.exe -c "import onnxruntime as o; print(o.__version__, o.get_available_providers())"
```

That example assumes `.venv` is the clean environment you chose for GPU. Do not run both install variants into it. If CUDA fails, use the CPU environment and leave the app's CUDA checkbox unchecked. No automatic OOM fallback is implemented.

## Model preparation

Store local weights, upstream checkouts and manifests under `models/local/` or another local directory. This location is ignored by Git. Example manifests under `models/` are templates and deliberately fail checksum validation until real models are registered. The app never downloads weights.

### YOLOX person model

Use [official YOLOX releases](https://github.com/Megvii-BaseDetection/YOLOX/releases) or its [model zoo](https://github.com/Megvii-BaseDetection/YOLOX#benchmark). Prefer a fixed-batch-one YOLOX-tiny 416x416 COCO ONNX export for the first low-memory trial. If an official ONNX file already matches that contract, registration is enough; otherwise use a **separate conversion environment** with upstream dependencies and official weights.

[Official export options](https://github.com/Megvii-BaseDetection/YOLOX/blob/main/tools/export_onnx.py) include `--decode_in_inference`. For example, inside a trusted upstream checkout with its export environment installed:

```powershell
# Example executed from the upstream YOLOX checkout, not this project's root:
python tools/export_onnx.py -n yolox-tiny -c PATH_TO_OFFICIAL_WEIGHTS --output-name PATH_TO_YOLOX_TINY.onnx --no-onnxsim
```

Resolve those placeholders to actual paths. Upstream dependency compatibility may need pinning; record its commit and versions rather than altering the app environment. Do not use untrusted pickle checkpoints. Default upstream export leaves boxes undecoded; if you deliberately add `--decode_in_inference`, also pass `--decoded-boxes` below. From this project's root, using the app's environment:

```powershell
.\.venv\Scripts\python.exe .\tools\register_yolox.py .\models\local\yolox_tiny.onnx --size 416
```

This checks metadata and writes the SHA-256 manifest, but does not prove detection accuracy. Confirm box positions on a known frame. A YOLOv8/11/other ONNX file is not compatible with this adapter.

### TrackNet shuttle model

Obtain a trusted [TrackNetV3 checkout](https://github.com/qaz812345/TrackNetV3) and the checkpoint linked by its [official inference instructions](https://github.com/qaz812345/TrackNetV3#inference). Keep its MIT notice with the weights. Choose the TrackNet checkpoint, not InpaintNet. Use a separate conversion environment containing PyTorch and ONNX; obtain platform-specific PyTorch installation instructions from [pytorch.org](https://pytorch.org/get-started/locally/).

```powershell
# Example conversion environment, on target PC only:
py -3.11 -m venv .venv-convert
.\.venv-convert\Scripts\python.exe -m pip install torch onnx
.\.venv-convert\Scripts\python.exe .\tools\export_tracknet.py --source .\models\local\TrackNetV3 --checkpoint .\models\local\TrackNet_best.pt --output .\models\local\tracknet.onnx --fps 30
```

The converter reads `param_dict.seq_len`, `param_dict.bg_mode` and `model` from the checkpoint. It only supports RGB / median-concat contracts and uses safer tensor-only loading; do not bypass a rejected checkpoint with unsafe deserialization. It creates a manifest containing SHA-256 and the declared cadence. Check the training/validation cadence for your weights; the default 30 fps is a starting contract requiring footage validation, not a claim that all weights support all cadences.

Before use, compare ONNX and PyTorch heatmaps on the same input tensor and inspect a known rally. Export success alone is not parity validation. Current inference uses nonoverlapping temporal sequences and no InpaintNet, so upstream ensemble/rectification accuracy does not carry over. If the model misses your far-court shuttle, annotate representative frames and plan fine-tuning rather than hiding the misses with invented points.

In the app: select both real `.json` manifests, save, prepare the proxy **after selecting the shuttle manifest**, mark the court, suggest/draw and confirm the roster/type, save again, then analyse. Changing cadence requires preparing again. Keep experimental auto-awards off for the first benchmark. Review contacts, pending points and spectator windows before exporting.

## Build and reproducibility

Run `run_checks.ps1` first, then `npm run desktop:build` for NSIS. Development dependencies are downloaded here for the first time; commit the resulting npm/Cargo lockfiles, icons and a version record after review. Record `pip freeze` to a reviewed text file on the testing PC; remove any private package URLs/credentials before sharing it. The first source commit has no fabricated resolved lockfiles.

The installer bundles the authored Python package **source**, not a Python interpreter, FFmpeg, weights or CUDA DLLs. Confirm the installed build finds the external `MIDMINTON_PYTHON` interpreter and resources correctly. A completely self-contained offline installer remains future packaging work.
